## Abstract
This proposal introduces the **ADAM (A Decentralized Approach Model)** cooperative consensus mechanism. ADAM splits block validation and creation into three distinct cooperative phases: leader election, lightweight puzzle solving, and block signature aggregation. It prevents mining pool centralization, selfishness, and leader DoS attacks by requiring cooperative work from multiple elected nodes (11 miners and 1 coordinator) to validate each block.

## Motivation
Traditional Proof-of-Work (PoW) protocols suffer from pool centralization, where a few entities dominate block generation. They are also vulnerable to selfish mining and targeted Denial-of-Service (DoS) attacks on block producers whose identity is predictable. Standard Proof-of-Stake (PoS) protocols suffer from "nothing-at-stake" forks. 

ADAM resolves these vulnerabilities by forcing a group of validator nodes to collaborate:
* The identity of the block producer (the Coordinator) is hidden and unpredictable until block generation.
* The block hash depends on the sequential cryptographic work of multiple independent miners, neutralizing selfish mining.
* Masternodes provide the baseline election pool, preventing Sybil attacks.

## Specification

### 1. Deterministic Leader Election (SSLE)
At each block height $H$, the active validator pool (masternodes and registered miners) is queried. The network utilizes a Single Secret Leader Election (SSLE) protocol to select $N = 11$ Miners and $1$ Coordinator based on a rolling random seed:

$$\text{Seed}_H = \text{Hash}\left(\text{Seed}_{H-1} \mathbin{\Vert} \text{VRFProof}_{H-1}\right)$$

Where $\text{VRFProof}_{H-1}$ is the deterministic hybrid signature generated by the Coordinator of block $H-1$.

Every node $i$ in the active pool is ranked:

$$\text{Rank}_i = \text{Hash}\left(\text{Seed}_H \mathbin{\Vert} \text{PubKey}_i\right)$$

The pool is sorted in ascending order of their rank. The first $N$ nodes are elected as Miners, and the next node is elected as the Coordinator.

---

### 2. Lightweight PoW Puzzle Solving
Elected miners must prove they performed work by solving a lightweight cryptographic puzzle. The difficulty target is relaxed using a bit-shift multiplier:

$$\text{scaledTarget} = \text{Target} \ll \text{activeShift}$$

The shift value is height-dependent:
* $\text{activeShift} = 10$ (or $12$) if block height $< 705$.
* $\text{activeShift} = 6$ if block height $\ge 705$.

Miners solve the following target equation:

$$\text{PuzzleHash}_i \le \text{scaledTarget}$$

Where $\text{PuzzleHash}_i$ is computed using a 3-permutation selector scheme based on X11/X16R-like permutations of 18 energy-efficient hash functions:

$$\text{PuzzleHash}_i = \text{algo1}\left( (i + 1) \times \text{algo2}\left( (i + 1) \times \text{algo3}(\text{Challenge}) \right) \right) \pmod{2^{256}}$$

And the challenge data is defined as:

$$\text{Challenge} = \text{Seed}_H \mathbin{\Vert} \text{MinerPubKey}_i \mathbin{\Vert} \text{Nonce}_i$$

---

### 3. Block Hashing Chain (Stateless Hashing)
To bind the block header cryptographically to the work of all elected miners, the block hash ($H_{\text{block}}$) is computed by sequentially chaining the hashing operations of all elected miners.

For a serialized block header $S$:
1. For each round $i \in \{0, \dots, M-1\}$ (where $M$ is the number of miners), we calculate an odd coprime multiplier $m_i$ to preserve hash entropy:

   $$\text{roundHash}_i = \text{Hash}\left(\text{hashPrevBlock} \mathbin{\Vert} i\right)$$

   $$m_i = \max\left(\text{roundHash}_i[0] \mid 1, 3\right)$$

2. The rounds are chained sequentially:
   - **Round 0**:
     * Derive $\text{algo1}$, $\text{algo2}$, and $\text{algo3}$ for miner $0$.
     * Compute:

       $$H_0^{(3)} = \text{CalculateAdamPuzzleHash}(\text{algo3}, S)$$

       $$H_0^{(2)} = \text{CalculateAdamPuzzleHash}\left(\text{algo2}, \left( H_0^{(3)} \times 1 \right) \pmod{2^{256}}\right)$$

       $$H_0 = \text{CalculateAdamPuzzleHash}\left(\text{algo1}, \left( H_0^{(2)} \times 1 \right) \pmod{2^{256}}\right)$$

     * Apply multiplier:

       $$H_{\text{prev}} = (H_0 \times m_0) \pmod{2^{256}}$$

   - **Round $i > 0$**:
     * Derive $\text{algo1}$, $\text{algo2}$, and $\text{algo3}$ for miner $i$.
     * Compute:

       $$H_i^{(3)} = \text{CalculateAdamPuzzleHash}(\text{algo3}, H_{\text{prev}})$$

       $$H_i^{(2)} = \text{CalculateAdamPuzzleHash}\left(\text{algo2}, \left( H_i^{(3)} \times (i + 1) \right) \pmod{2^{256}}\right)$$

       $$H_i = \text{CalculateAdamPuzzleHash}\left(\text{algo1}, \left( H_i^{(2)} \times (i + 1) \right) \pmod{2^{256}}\right)$$

     * Apply multiplier:

       $$H_{\text{prev}} = (H_i \times m_i) \pmod{2^{256}}$$

3. The final output is the block hash:

   $$H_{\text{block}} = H_{\text{prev}}$$

---

### 4. Quorum-Resilient Responding
To prevent offline or lagging miners from freezing block production, block templates can be generated and propagated if a minimum quorum threshold ($T$) of solutions is received.
* **Mainnet / Regtest**: $T = 7$ out of $11$ miners.
* **Testnet**: $T = 3$ out of $11$ miners.

If an elected miner's solution is missing but the quorum threshold is met, the Coordinator substitutes the missing miner's solution with an empty vector placeholder:

$$\text{vAdamSolutions}[i] = \text{std::vector<unsigned char>()}$$

This maintains the 1:1 positional alignment between miners and solutions inside the block header. Empty placeholders are treated as invalid/skipped solutions during block validation and do not count toward the quorum verification check.

## Backward Compatibility
ADAM is activated conditionally based on block height:
* Activated on Testnet/Regtest/Mainnet at block height `200`.
* Fallback Mode (Block Version 11) runs during the bootstrap phase where the network lack masternodes.
* Standard Mode (Block Version 12) enforces the full masternode election loop and is activated at block height `2000` (Mainnet), `400` (Testnet), or `300` (Regtest), or via the Spork `SPORK_21_ADAM_STANDARD_MODE` (`10020`).
