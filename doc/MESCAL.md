# MESCAL Specification

**Minimalistically Envisioned Smart Contract Assembling Language**  
*Version 1.0.0 — Official Technical Specification*

---

## 1. Introduction

MESCAL (Minimalistically Envisioned Smart Contract Assembling Language) is a JSON-based declarative language designed to define, assemble, and serialize Smart Contracts for KristaTech (KRISTA) compatible blockchains. 

Traditional smart contract languages (such as Solidity or Plutus) require specialized developers, heavy runtime virtual machines (VMs), and introduce substantial security attack surfaces. MESCAL solves these issues by adhering to the **KISS (Keep It Simple, Stupid)** principle: it acts as a high-level, human-readable, and machine-parsable JSON representation of Bitcoin-like stack script instructions (`CScript`).

### Why MESCAL?
1. **Accessibility**: Allows users and applications to create, sign, and execute smart contracts without needing low-level assembly or compilation knowledge.
2. **Safety**: Operates on a restricted, deterministic instruction set matching blockchain opcodes, eliminating execution-time re-entrancy attacks and gas calculation issues.
3. **Interoperability**: JSON is natively parsed and generated by almost all modern programming languages, making explorer integration, client-side wallets, and backend services trivial.

---

## 2. Core Philosophy & JSON Formatting

Every MESCAL script is a declarative JSON tree.
* **Order Sensitivity**: Arrays and JSON objects are parsed in strict order of appearance (from the first element to the last).
* **Self-Contained Schemas**: A contract definition compiles directly into linear blockchain bytecode.
* **High-Level Variables**: JSON keys act as parameter bindings, allowing off-chain clients to bind user inputs (such as keys, timestamps, or limits) directly into templates before transaction submission.

## 3. Structural Specification & Component Types

A MESCAL program consists of three fundamental structural types: `basic`, `condition`, and `contract`.

### 3.1. Basic Elements (`basic`)
A `basic` block represents a primitive script operator or static value wrapper. It maps directly to one or more Bitcoin script opcodes.

```json
{
  "type": "basic",
  "name": "Unique-Identifier",
  "role": "<op-code-role>",
  "inputs": [
    {
      "type": "<data-type>",
      "name": "Parameter-Name",
      "value": "<data-value>"
    }
  ]
}
```

#### Supported Roles & Opcodes
* `hash160`: Performs SHA256 followed by RIPEMD160. Maps to `OP_HASH160`.
* `check-signature-verification`: Verifies a signature against a public key. Maps to `OP_CHECKSIGVERIFY`.
* `equalverify-checksig`: Verifies that a public key hash matches the input, then verifies the signature. Maps to `OP_DUP OP_HASH160 <pubkeyhash> OP_EQUALVERIFY OP_CHECKSIG`.
* `number`: Pushes a numerical constant onto the stack. Maps to standard script integers (e.g. `OP_1`, `OP_2` or byte arrays).
* `multi-signature`: Pushes public keys and enforces multisig verification. Maps to `<m> <pubkeys...> <n> OP_CHECKMULTISIG`.
* `lock-time`: Locks transaction spends until a target time or height. Maps to `<locktime> OP_CHECKLOCKTIMEVERIFY OP_DROP`.

---

### 3.2. Condition Elements (`condition`)
A `condition` block implements control flow using conditional execution branches (comparisons and boolean evaluations).

```json
{
  "type": "condition",
  "name": "Unique-Condition-Name",
  "role": "if-condition",
  "expressions": [
    {
      "required": true,
      "type": "basic",
      "name": "Trigger-Variable"
    }
  ],
  "true": [
    { "type": "basic", "name": "Success-Branch-Action" }
  ],
  "false": [
    { "type": "basic", "name": "Failure-Branch-Action" }
  ]
}
```
* **Script Mapping**: Under the hood, this compiles to `OP_IF ... OP_ELSE ... OP_ENDIF` structures.

---

### 3.3. Assembled Contracts (`contract`)
A `contract` is a top-level schema containing sequentially evaluated actions (`basic` or `condition` blocks). It acts as the final script template used to lock transaction outputs (UTXOs).

```json
{
  "type": "contract",
  "name": "My-Contract-Name",
  "description": "Human readable documentation for this contract.",
  "actions": [
    { "type": "basic", "name": "Step-1-Action" },
    { "type": "condition", "name": "Step-2-Conditional" }
  ]
}
```

## 4. Complete Specifications & Examples

### 4.1. HASH160 Verification
* **CScript Equivalent**: `OP_HASH160 <Hash160(inputs[0])> OP_EQUALVERIFY`

```json
{
  "type": "basic",
  "role": "hash160",
  "name": "Hash-Validation",
  "inputs": [
    {
      "type": "string-or-number",
      "name": "Data-to-Hash",
      "value": "KristaTechSmartContractInput"
    }
  ]
}
```

---

### 4.2. Pay-to-Public-Key-Hash (P2PKH) equivalent
* **CScript Equivalent**: `OP_DUP OP_HASH160 <pubkeyhash> OP_EQUALVERIFY OP_CHECKSIG`

```json
{
  "type": "basic",
  "role": "equalverify-checksig",
  "name": "Standard-P2PKH",
  "inputs": [
    {
      "type": "pubkeyhash",
      "name": "Recipient-PubkeyHash",
      "value": "b5a9c9f285d893ce71ab9de8f5c09d765ee982ba"
    }
  ]
}
```

---

### 4.3. Multi-Signature (2-of-2)
* **CScript Equivalent**: `2 <pubkey1> <pubkey2> 2 OP_CHECKMULTISIG`

```json
{
  "type": "basic",
  "role": "multi-signature",
  "name": "Escrow-Multisig",
  "inputs": [
    {
      "type": "number",
      "name": "n",
      "value": 2
    },
    {
      "type": "number",
      "name": "m",
      "value": 2
    },
    {
      "type": "array",
      "name": "Signatures",
      "value": [
        "02ee1fb80068f574b0d110009f110f703161cd358889a7bc48c613aa898136660f",
        "03ee1fb80068f574b0d110009f110f703161cd358889a7bc48c613aa898136660a"
      ]
    }
  ]
}
```

---

### 4.4. Time-Locked Deposit (CLTV)
* **CScript Equivalent**: `<expiry-time> OP_CHECKLOCKTIMEVERIFY OP_DROP`

```json
{
  "type": "basic",
  "role": "lock-time",
  "name": "Time-Lock-Enforcement",
  "inputs": [
    {
      "type": "timestamp-or-block-height",
      "name": "Lock-Until",
      "value": 1780718400
    }
  ]
}
```

---

### 4.5. Conditional Execution (If-Else)
* **CScript Equivalent**: `OP_2 OP_IF <expiry-time> OP_CHECKLOCKTIMEVERIFY OP_DROP OP_1 OP_ELSE OP_HASH160 <pubkeyhash> OP_EQUALVERIFY OP_ENDIF`

```json
{
  "type": "condition",
  "role": "if-condition",
  "name": "Multi-Path-Resolution",
  "expressions": [
    {
      "required": true,
      "type": "basic",
      "name": "Constant-Value-2"
    }
  ],
  "true": [
    {
      "type": "basic",
      "name": "Time-Lock-Enforcement"
    },
    {
      "type": "basic",
      "name": "Constant-Value-1"
    }
  ],
  "false": [
    {
      "type": "basic",
      "name": "Hash-Validation"
    }
  ]
}
```

---

### 4.6. Assembled Freezing Funds Contract
Locks funds in a UTXO until a target date. Once the target date passes, the recipient can spend it by providing their signature.
* **CScript Equivalent**: `<expiry-time> OP_CHECKLOCKTIMEVERIFY OP_DROP OP_DUP OP_HASH160 <pubKeyHash> OP_EQUALVERIFY OP_CHECKSIG`

```json
{
  "type": "contract",
  "name": "Freezing-Funds",
  "description": "Freezes coins in a UTXO until a future timestamp, then allows spending with recipient key.",
  "actions": [
    {
      "type": "basic",
      "name": "Time-Lock-Enforcement"
    },
    {
      "type": "basic",
      "name": "Standard-P2PKH"
    }
  ]
}
```

## 5. Compiler Implementation Guidelines

To deploy MESCAL contracts onto KristaTech (KRISTA) nodes, a parser must process the JSON tree and output the serializable `CScript` bytes.

### 5.1. Parsing Order
The compiler must parse the top-level `"actions"` array sequentially:
1. Load action definitions recursively.
2. Resolve referenced parameters and inject variables.
3. Emit matching opcode equivalents onto the byte compilation stream.

### 5.2. Validation Rules
Before emitting CScript bytecode, the compiler must assert the following safety checks:
* **Stack Depth Limit**: Verify that the generated opcodes do not exceed the blockchain’s maximum stack depth limit (usually 1000 items).
* **Disabled Opcodes**: Prevent injection of prohibited opcodes (e.g. `OP_CAT` or `OP_LSHIFT`) which are disabled on the consensus layer to prevent memory exhaustion.
* **Time Lock Assertions**: Ensure that any `lock-time` actions place the locktime opcode (`OP_CHECKLOCKTIMEVERIFY`) before signature checking to avoid transaction malleability issues.
